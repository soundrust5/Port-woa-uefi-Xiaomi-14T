# Контракт LK: первый статический проход

Проанализирован точный `lk-payload.bin`, SHA-256 `6afd84aefda089681f0ec4a224c6710228f525ec312bfa2532977be9e4496580`. Его связь с исходным и считанным LK описана в `LK-FRAMEBUFFER-ANALYSIS.md`. Ниже адреса инструкций — виртуальные адреса LK при базе `0xffff000050700000`, не адреса размещения нашего payload.

Проверяемые фрагменты с исходными байтами: `evidence/extracted/2026-09-14/lk-analysis/handoff-evidence.asm`; повторное извлечение — `python tools/extract_lk_handoff.py`. Отдельно [сопоставлены журнал и образы](LK-HANDOFF-LOG.md): stock kernel имеет legacy LZ4, vendor_boot указывает kernel address `0x40000000` и DTB address `0x47c80000`. Это ещё не разрешение на размещение Mu в этих областях.

## Формат kernel payload

В исследованном пути `boot_linux_fdt` после поиска reservation и проверки kernel target вызывается распаковщик по адресу `0xffff00005070e90c` (call site `0xffff00005070fd98`). Входы этого вызова: источник x23, назначение из локальной переменной, размер входа w24, размер области w20.

Диспетчер `0xffff00005070e948..0xffff00005070e998` различает:

| Начальные байты | Ветка |
|---|---|
| `1f 8b` | gzip; дальнейший код дополнительно проверяет method и flags |
| `02 21 4c 18` | legacy LZ4, не современный LZ4 frame |
| остальные | `0xffff00005070ec10`, сообщение `No magic number of compression is found!` и вызов обработчика ошибки |

Ровно эти машинные инструкции выполнены в Unicorn для шести случаев, включая наш сырой entry и его gzip-вариант. Отчёт: `evidence/lk-compression-dispatch-tests.json`. Это тест распознавания формата; весь распаковщик, AVB, загрузочный контейнер и телефон не исполнялись. Нельзя переносить вывод на каждый возможный режим LK без проверки его маршрута.

`diagnostic/prepare_kernel.py` создаёт `diagnostic/build/entry.bin.gz` с нулевым timestamp, без filename/optional flags, и проверяет распаковку средствами Python до исходных байтов. Это кандидат kernel payload для дальнейших проверок на ПК, не boot.img. Размер 323 байта объясняется тем, что большая часть исходных 16816 байт — нулевой стек внутри образа; после распаковки нужен весь исходный размер.

## Переход через secure firmware

После сообщения `lk finished --> jump to linux kernel` код `0xffff000050710038..0xffff000050710058` передаёт в trampoline:

- x0: адрес stub `0xffff000050711398`;
- x1: `0xc2000115`;
- x2: x19, тот же kernel target, который печатается в booting-linux log;
- x3: x22, тот же DTB target, который печатается в этом log;
- x4: 0.

Функция `0xffff00005071a048` сохраняет аргументы, вызывает подготовительные процедуры и преобразование адреса stub, затем передаёт их в `0xffff000050719de4`. Эта последняя последовательность переставляет регистры, устанавливает VBAR_EL1, очищает бит M в SCTLR_EL1, выполняет ISB/TLBI и `br x4`. Stub по смещению `0x11398` делает `mov x4,#1; smc #0`.

На инструкции SMC получаются x0=`0xc2000115`, x1=kernel target, x2=DTB target, x3=0, x4=1. Это конкретный интерфейс LK к secure firmware. Семантика x4 и режим выхода secure firmware здесь не установлены. Нельзя объявить x0 payload равным DTB или назначить EL2 только из этих регистров: SMC handler ещё может их изменить. Очищение M до SMC также не доказывает состояние cache/MMU после SMC.

## Что реализовано и что дальше

Формат несжатого пробника исключён для исследованного пути; создан и проверен gzip-кандидат. Добавлена утилита `tools/lk_string_xrefs.py` для воспроизводимого поиска простых ADR/ADRP+ADD ссылок на строки в закреплённом LK. Она намеренно не является полным анализатором потока данных.

Следующий узкий участок — обработчик `0xc2000115` в точном secure firmware и продолжение display shutdown перед SMC. До этого не выбираем FD/heap из донорских значений. Для минимального пробника стек уже включён внутрь загружаемого образа, но доступность этого образа на запись и наблюдаемый сигнал ещё требуют подтверждения. Прошивка и перезагрузка телефона не выполнялись.

Подготовлен точный ATF для продолжения: stock `tee.img` байт-в-байт совпадает с префиксом считанного `tee_b.img`. Первый MTK payload `atf` начинается со смещения `0x200`, длина 962168 байт; извлечён в `evidence/extracted/2026-09-14/atf-analysis/`, хеши в `manifest.json`. Журнал строка 7007 сообщает загрузку 962168 байт по LK VA `0xffff000048800000`. В ATF найдены соседние значения `0x82000115`, `0xc2000115` и указатель на строку `MTK_SIP_KERNEL_BOOT` около смещения `0x67ea8`. Это ориентир для разбора диспетчера; назначение полей таблицы и полный обработчик пока не подтверждены.
