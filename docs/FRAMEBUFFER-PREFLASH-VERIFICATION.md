# Проверка соответствия framebuffer до следующей прошивки

Выполнена главным агентом 2026-09-15. Телефон не прошивался, регистры и память
на телефоне не изменялись. Использованы сохранённые точные BL2/LK, DT и expdb.

## Новое доказательство: адрес доходит до записи OVL

Ранее подтверждалось заполнение структуры слоя. Теперь прослежено её дальнейшее
использование в точном BL2_EXT SHA-256
`74f9bf4faafc694193dda1dc1f9bef40338cd389278781292d9f8044d4d3a35a`:

1. `0xffff000078036b90` переносит входной addr в конфигурацию пути; копирование
   поля через `0x36d58/0x36d6c` не изменяет адрес.
2. `0xffff000078036e04` вызывает config dispatcher `0xffff00007802f5d0`.
   Он вызывает module driver slot +0x18.
3. Конструктор таблицы `0xffff00007802e5fc` связывает module 1 с объектом
   `0xffff0000780df478`, callback +0x18 = `0xffff000078031788`.
   Module 1 присутствует в обоих кандидатах direct-link scenario 0 и 18;
   выбор зависит от runtime panel parameters, его не подменяем предположением.
4. OVL config читает addr в w4 по `0xffff000078031a20` и вызывает функцию
   настройки слоя `0xffff000078030cf4` через `0xffff0000780319dc`.
5. В функции слоя w4 сохраняется в w22. Инструкции `0x31024/0x3102c`
   вычисляют addr + src_y*pitch + src_x*bytes_per_pixel, затем `0x3104c`
   записывает результат в регистр layer_base+0xf40.

Для module 1, layer 0 база регистров в LK VA — `0xffff000014402000`.
Она получена двойным чтением таблицы (0x103498 → 0x780df010 → база), а не
выбрана по сходству адресов с другим MediaTek.

| Поле | Регистр в адресном пространстве BL2 | Результат при параметрах слоя 0 |
|---|---|---|
| Адрес пикселей | 0xffff000014402f40 | 0xfcc2f000 |
| Pitch, младшие 16 бит | 0xffff000014402044 | 0x1380 = 4992 |
| Размер | 0xffff000014402038 | 0x0a9804c4 = 2712×1220 |

`tools/verify_bl2_scanout_address.py` исполняет **оригинальные инструкции** этой
функции в Unicorn с моделируемыми регистрами MMIO. Проверены основной слой,
отдельный вторичный слой и ненулевое смещение src_x/src_y; последний случай
проверяет формулу адреса, а не только совпадение констант. Отчёт:
`evidence/bl2-scanout-address-analysis.json`.

Это доказательство работы функции при переданных параметрах, а не чтение
реального OVL после watchdog. Значения alpha/key в тесте заданы для валидного
вызова и не выдаются за снимок реального состояния панели.

## Сопоставление с остальными данными

- Сохранённый LK log: fb_va=0xffff000000200000, fb_pa=fb_pa_k=0xfcc2f000;
  main-LK logo writer использует этот VA с pitch 4992.
- DT резервирует тот же framebuffer; offset основного слоя нулевой.
- Второй probe доказал запись и чтение пикселей по CPU-visible 0xfcc2f000.
- Отдельный boot-menu буфер 0xfd922000 не подставляется функцией вместо layer 0.
- В main LK после записи пикселей выполняется отдельная цепочка display mutex
  и DSI trigger. В наших первых двух probe её нет.

## Что остаётся недоказанным

1. Преобразование CPU IPA→PA через stage-2 при входе probe. HCR_EL2.VM=1;
   наличие успешного readback не доказывает identity mapping.
2. Состояние display IOMMU/bypass и активного слоя именно после handoff.
   Запись framebuffer-адреса в OVL сама по себе не доказывает обход IOMMU.
3. Продолжение передачи кадра на command-mode панель после изменения RAM.

Повторный поиск в полном сохранённом expdb второго теста (SHA-256
`8e5c055ea2e29eb078be917a433eb896b2f5383433f0bd0ebbdf70ec7a53aa3d`)
не нашёл текстовых имён VTTBR/VTCR, IOMMU или адреса 14402f40.
Это **не** доказательство отсутствия любых бинарных сведений о них: формат
всех внутренних crash records ещё не разобран. Снимка таблиц трансляции,
который можно надёжно привязать к probe, у нас пока нет.

## Вывод до прошивки

Расчёт base/pitch и путь записи адреса в OVL подтверждены точным бинарником.
Оснований менять 0xfcc2f000 наугад нет. Полное утверждение «probe пишет в тот же
физический буфер, который читает дисплей после handoff» пока было бы преждевременным.

Образ ramoops остаётся неизменным: он проверяет сохранность журнала и не добавляет
непроверенные MMIO-доступы. После проверки канала журнала следующая диагностика
должна фиксировать исходные содержательные участки logo surface и обоснованные
регистры display path на входе, до перерисовки. Текущее состояние Android этого
снимка не заменяет.
