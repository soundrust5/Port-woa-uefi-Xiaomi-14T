# План проекта

Версия 0.2, 2026-09-14. По выбору пользователя база — Mu-Silicium, исходная ревизия для аудита `964a886f3d1ad3f35137435b11287c8d6827437b`. Подробный первый этап описан в [HARDWARE-SURVEY-PLAN.md](HARDWARE-SURVEY-PLAN.md), результаты — в [HARDWARE-SURVEY-INITIAL.md](HARDWARE-SURVEY-INITIAL.md). Детали последующих этапов уточняются после измерений.

## Цели и последовательность

| Этап | Результат | Критерий завершения |
|---|---|---|
| M0. Исходное состояние | Паспорт телефона и конкретный путь восстановления | Известны система, слоты, изменённые загрузочные разделы; сохранены доступные нужные образы с хешами; описан возврат из неудачного теста |
| M1. Контракт загрузки | Понимание формата образа, памяти и входа в код | Документ с источником каждого используемого параметра; выбран способ доставки и раннего наблюдения |
| M2. Сборка на ПК | Повторяемая ARM64-сборка и проверка общего кода | Зафиксированы версии и исходники; эталон EDK2/EFI-приложения работает в QEMU; локальные проверки формата проходят |
| M3. Собственный код на телефоне | Минимальный диагностический payload | Новый маркер с идентификатором сборки повторяется в трёх отдельных запусках; сохранено наблюдение и выполнен возврат к Android |
| M4. Минимальный UEFI | EDK2 запускает отдельное EFI-приложение | Подтверждены этапы EDK2, приложение и успешные вызовы выбранных Boot Services; результат повторяется |
| M5. Практическая среда UEFI | Вывод, ввод и чтение носителя | Видна консоль/меню, работает доступный ввод, контрольный файл прочитан с проверкой хеша |
| M6. Передача управления ОС | Работоспособность интерфейса UEFI → ОС | Есть журнал перехода через ExitBootServices и дальнейшего выполнения; отдельно оцениваются Linux и Windows |
| M7. Windows ARM64 | Поэтапная проверка Windows и драйверов | Раздельно фиксируются Boot Manager, ядро/WinPE, установка, рабочий стол и пригодность к использованию |

Текущий статус: M0/M1 в работе; выполнены сбор через root/ADB, копирование 22 загрузочных разделов и GPT, извлечение/сравнение DT, сверка PL/LK и Linux memblock/CMA, разбор установленного DRM. Результаты памяти/экрана: [MEMORY-RECONCILIATION.md](MEMORY-RECONCILIATION.md) и [FRAMEBUFFER-CONTRACT.md](FRAMEBUFFER-CONTRACT.md). M2–M7 не завершены. Без полного контракта памяти/вывода это не готовность к аппаратному эксперименту.

Первый код: [ARM64-пробник и framebuffer-библиотека](../diagnostic/README.md) собираются отдельно от Mu. Клонирован Mu на выбранной ревизии, внесены локальные patches раннего стека и вывода. M2 начат, но полная сборка Mu и эталон QEMU ещё не выполнены; M3 не проводился.

## M0 — исходное состояние и восстановление

Собрать паспорт по `DEVICE.md`, сведения о слотах и версии системы. Сверить работающий аппарат с доступной прошивкой. Отдельно учесть KernelSU, TWRP и возможные изменения AVB. По возможности сохранить текущие загрузочные компоненты: заводские образы и установленные модифицированные образы имеют разное назначение.

Описать точный путь восстановления именно выбранного эксперимента: доступный режим, нужные файлы, целевой раздел/слот, ожидаемые результаты. A/B само по себе не гарантирует рабочий резервный слот. Не считать сервисное восстановление MediaTek доступным без проверки необходимых инструментов и авторизации.

На ранних этапах не планируем изменение preloader, LK, TEE, GPT или переразметку накопителя. Для первого запуска предпочитаем временную загрузку, если её работоспособность подтверждена; иначе отдельно проектируем минимальное изменение загрузочного раздела с восстановлением. Необходимость записи не следует из наличия fastboot на ПК.

## M1 — исследование штатной загрузки

1. Разобрать boot, init_boot и vendor_boot официальными инструментами AOSP с фиксацией версии. Сохранить заголовки, размеры, cmdline, bootconfig и сведения об упаковке/сжатии. Не переносить рецепты заголовков v0/v2 на обнаруженный v4 [S4].
2. Извлечь DTB/DTBO, установить выбранную конфигурацию платы. По возможности сопоставить с деревом, которое реально передаётся работающему ядру: загрузчик может дополнять его.
3. Составить карту RAM: доступные диапазоны, firmware, secure carveouts, framebuffer, ramdisk, DTB, стек, образ EDK2 и область диагностики. Проверять пересечения и выравнивание. Размер раздела и адрес в scatter не заменяют эту карту.
4. Сопоставить исходники Xiaomi с прошивкой. Ищем сведения о UART, watchdog, дисплее, таймере, GIC, PSCI и памяти. Несовпадение Android U в исходниках и имени Android 16 у архива фиксируем явно.
5. При недостатке данных изучить LK и ранний путь ядра. Стандартный контракт AArch64 Linux — исходная гипотеза для входного адаптера, а не измерение состояния конкретного телефона [S5].
6. Выбрать канал доказательства выполнения согласно `OBSERVABILITY.md`. Пока он не выбран и не обоснован, создание нового образа не решает проблему отсутствия диагностики.

Выход: `boot-contract.md` с таблицей «параметр — значение — источник — способ проверки — статус». Его создаём после анализа, без выдуманных значений.

## M2 — сборочная среда и проверки на ПК

База выбрана пользователем: Mu-Silicium. Закрепить ревизию и submodules, проверить ранний вход, память, вывод, сборку и зависимости по документу MU-PLATFORM-REQUIREMENTS.md. Project Mu основан на EDK2 [S10, S11]. В WSL обнаружен Ubuntu с DTC 1.7.2; компилятор и полноценная сборочная среда ещё не подготовлены.

В дереве выбранной ревизии есть MT6768Pkg, MT6789Pkg и общий MediaTekPkg; пакетов degas/MT6897 нет. Делаем собственную поддержку платформы, используя донорский код только после проверки конкретной функции. Чистый TianoCore/ArmVirt остаётся возможным эталоном общих EFI-тестов, не выбранной базой телефонного порта [S3, S6, S10].

Собрать эталонный ArmVirtPkg для QEMU и маленькое EFI-приложение. Это проверяет инструменты и общие механизмы EDK2. QEMU virt не моделирует наш MT6897 и не подтверждает адреса регистров, загрузчик, дисплей или работоспособность образа на телефоне.

Проверки аппаратного артефакта на ПК: формат контейнера, диапазоны секций, размер, точка входа, выравнивание, отсутствие наложений, дизассемблирование самых первых инструкций. Сохранять ELF/map, журнал сборки, commit и SHA-256 каждого выдаваемого образа.

## M3 — минимальный диагностический payload

Сначала сделать маленький ARM64-код с минимальным количеством зависимостей. Он должен выдать уникальный маркер, показать последующую активность и позволить локализовать остановку. Это самостоятельный результат до EDK2.

Нужны: корректный вход, сохранение нужных параметров, безопасный стек, по возможности ранний обработчик исключений, подтверждённый канал вывода и обоснованное поведение watchdog. Не отключать watchdog записью по адресу от другой модели. Первый маркер желательно размещать до сложной инициализации.

После статических проверок подготовить одну карточку эксперимента. Пользователь получает конкретный образ, хеш, действия, ожидаемый результат и путь возврата. Меняем одну проверяемую гипотезу за эксперимент; сохраняем отрицательные результаты. Три успешных запуска — выбранный проектный критерий воспроизводимости, а не гарантия общей стабильности.

Если маркер не появился, статус «выполнение не подтверждено», а не «код точно не запустился». Сначала разбираем пригодность канала и этап загрузки.

## M4 — минимальный EDK2

Перенести уже проверенные условия входа и диагностику в пакет платформы. Подключать минимально необходимые части: ранний вход выбранной ARM-схемы EDK2, описание памяти, MMU/cache, таймер, обработку исключений, отладочный вывод, DXE и запуск встроенного EFI-приложения. Точные стадии зависят от выбранной базы; не требовать механически полного пути SEC → PEI для любой ARM-конфигурации.

EFI-приложение выдаёт собственный маркер и проверяет GetMemoryMap, AllocatePages/FreePages и таймерное ожидание с наблюдаемым результатом. Само наличие текста «UEFI» в нашем framebuffer-коде не доказывает работу служб UEFI. Начальное приложение можно встроить в firmware volume, поэтому UFS и USB не обязаны предшествовать этому этапу.

Сохранить обработку сбоев: если доступен вывод, показывать адрес исключения, причину, последний этап и build ID. Сначала добиться повторяемого минимального запуска, затем подключать дополнительные драйверы.

## M5 — полезный ввод-вывод

Отдельные задачи: GOP поверх подтверждённого framebuffer или собственный дисплейный путь; кнопки; доступный USB; источник загрузочных файлов. USB может понадобиться раньше, если выбран каналом диагностики, но не считается готовым только потому, что он работал в Android/fastboot.

Начать поддержку накопителя с чтения и проверяемого контрольного файла. Полноценный GPU-драйвер не нужен для простого вывода в framebuffer. Интерактивная Shell требует ввода; автоматическое тестовое EFI-приложение может работать без него.

## M6–M7 — ОС и Windows

Провести ранний кабинетный аудит Windows-поддержки MT6897 параллельно планированию, чтобы заранее выявить ограничения. Основную аппаратную работу над Windows начинать после минимального UEFI.

Возможный промежуточный тест — запуск Linux через UEFI: он помогает исследовать передачу памяти и управления, но не доказывает совместимость Windows и не является обязательной веткой проекта.

Для выбранной версии Windows составить отдельную матрицу: ACPI/SMBIOS, CPU/GIC/таймер, PSCI, память, runtime services, хранилище, вывод и доступная отладка. Проверить актуальные требования Windows 11 и статус CPU/TPM/Secure Boot отдельно от низкоуровневого исследовательского запуска. Общая SoC-документация Microsoft частично относится к старым версиям и сама по себе не является сертификатом совместимости [S7, S8].

UEFI-драйвер накопителя помогает загрузчику читать файлы; после передачи управления Windows нужен подходящий драйвер самой ОС. Android/Linux-драйверы нельзя просто загрузить в Windows. Исходники могут помочь понять оборудование, но перенос требует новой реализации под соответствующую модель драйверов [S9].

Разделить результаты Windows: (1) Boot Manager выполняется; (2) ядро начинает работать и даёт диагностику; (3) WinPE получает пригодные ввод/хранилище; (4) установка и рабочий стол; (5) стабильная система. Логотип Windows не закрывает все эти пункты.

Крупные отдельные направления: UFS/USB, питание и тепловой режим, дисплей/GPU, тачскрин, Wi-Fi/Bluetooth, звук, модем. Наличие доступного Windows ARM64-драйвера для каждого из них пока не установлено. Достижение M3–M5 остаётся ценным результатом, даже если Windows окажется ограничена.

## Организация совместной работы

Главный агент ведёт архитектуру, контракт загрузки, интеграцию и проверку опасных аппаратных предположений. По предложению пользователя GPT 5.6 Sol получает ограниченные задачи: разбор форматов, отчёты, утилиты анализа, проверку документации и независимый обзор. У задачи должны быть входы, границы файлов и критерий готовности. Ответ субагента — материал для проверки, не аппаратное доказательство.

Пользователь выполняет физические действия и сообщает точные наблюдения; учиться всему сразу не требуется. Перед каждым тестом объясняем цель обычными словами и даём короткую последовательность действий. Не запускаем автономную серию прошивок.

Общий порядок: одна гипотеза → один различимый эксперимент → сохранённые доказательства → обновление паспорта и плана. Если параметры неизвестны, следующий шаг должен добывать информацию, а не увеличивать объём предположений в коде.

## Ближайшая рабочая порция

1. Разобрать изменения init_boot/vendor_boot и назначение компонентов обоих слотов; базовые копии уже сохранены.
2. Сопоставить извлечённый DT с live DT и завершить карту reserved-memory/mblock и драйверных зависимостей.
3. Найти исходники видеотегов и LK handoff, определить boot framebuffer stride/format и необходимые ранние блоки.
4. Составить контракт загрузки, затем выбрать первый наблюдаемый сигнал и минимальный payload.

Срок до Windows заранее не назначаем. Оценку усилий обновляем по закрытым этапам и реальной доступности информации о платформе.
