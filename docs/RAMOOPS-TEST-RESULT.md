# Ramoops: первый аппаратный опыт и ошибка выравнивания

2026-09-15. Исходный boot_b восстановлен и проверен SHA-256 на телефоне;
Android завершил загрузку, root доступен. Все материалы сохранены в
`evidence/raw/ramoops-test-recovery/`, включая полный expdb и новый AEE HWT.

Нового console-ramoops нет. Файл debuglogger побайтово совпадает с прежней копией.
Следовательно, сохранение журнала через watchdog пока не подтверждено.

В новом watchdog-контексте PC=0x38061e14, LR=0x380615e0, SP=0x400048b0,
PSTATE=0xa20003c9 (EL2h), ESR_EL2=0x8200000e, ELR_EL2=FAR_EL2=0x200.
Это не успешный WFE-цикл probe. ESR указывает Instruction Abort от нижнего EL;
0x200 согласуется с попыткой входа в EL1 synchronous vector при VBAR=0.
Но VBAR_EL1/ESR_EL1 не сняты, поэтому первичное исключение прямо не доказано.
Старый успешный readback-контекст также остаётся в expdb и не относится к этому опыту.

## Подтверждённый дефект нового образа

В diagnostic_ramoops компилятор объединил побайтовое заполнение строки в
невыровненные stores. Первая такая инструкция сохранённого образа:

```asm
0x40000604: stur w9, [sp, #0x5f]
```

SP=0x400048b0, адрес 32-битной записи=0x4000490f. Перед этим функция выделяет
0x1c0 байт стека: 0x40004a70−0x1c0 = 0x400048b0, ровно как в watchdog.
Инструкция находится до первого обращения к console-области ramoops.
Для data accesses с Device-атрибутами такие невыровненные операции недопустимы.
Наш entry оставляет stage-1 MMU выключенным; обычная семантика C/компилятора
не гарантирует подходящих инструкций для такого режима.

Документация Arm по alignment и Device memory:
https://documentation-service.arm.com/static/671fa027ad463325b2325b91

Добавленный regression test перехватывает невыровненные accesses в Unicorn.
Старый бинарник воспроизводимо останавливается на 0x604 до первой записи в
console. Ранее default Unicorn и host sanitizers этого аппаратного ограничения
не моделировали. Предыдущая проверка не обнаружила этот дефект.

## Исправление

Новая отдельная сборка `diagnostic/build_ramoops_aligned.py` добавляет
`-mstrict-align`; старый ELF и образ сохранены для сопоставления с дампом.
`test_ramoops_alignment.py` проверяет старый и исправленный ELF на двух базах:
старый ловит ожидаемый дефект, исправленный доходит до ramoops_ok без
невыровненных обращений. Полные 12 вариантов entry/границ/CRC нового ELF проходят.

Новый образ: `artifacts/ramoops-aligned-test/boot-ramoops-aligned.img`.
SHA-256: `0f9bbcdbb3dfb747acf6cfb9b9929e8184bfcb138abaefc1eb9282735523e7ef`.
На телефоне ещё не проверялся. Нет утверждения, что этим доказано сохранение
pstore или исправлен дисплей: первая аппаратная причина пока косвенная,
stage-2 доступность console и reset retention остаются непроверенными.

Следующий опыт должен использовать исправленную сборку. Повторно прошивать
прежний ramoops-образ не следует. Более ранние успешные marker/readback тесты
этот дефект нового форматирования строки не опровергает.
