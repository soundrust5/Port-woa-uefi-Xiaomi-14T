# Аудит раннего кода и причин отсутствия маркера

Дополнение после аппаратного теста: этот аудит пропустил невыровненные
записи, сгенерированные компилятором в ramoops_probe.c. Они возникают до
публикации журнала. [Разбор дефекта, исправление и новая проверка](RAMOOPS-TEST-RESULT.md).
Прежний ramoops-образ повторно не использовать.

Проверка от 2026-09-15: два диагностических образа, ramoops, entry/marker/readback, упаковка, watchdog-дампы и штатный display path. Анализ сохранённых данных, без записей на телефон.

## Проверка гипотезы «упал и завис до watchdog»

Повторно выполнены verify_first_watchdog.py и verify_second_watchdog.py.
Хеши raw payload и дампов совпадают, PC/LR/SP согласованно относятся к разным
сохранённым образам:

| Опыт | PC | LR | SP | Значение |
|---|---|---|---|---|
| Первый | 0x40000104 | 0x400000fc | 0x400044c0 | цикл после возврата из marker |
| Второй | 0x4000011c | 0x400000fc | 0x40004680 | diagnostic_readback_ok |

Цикл содержит WFE и переход обратно, watchdog не обслуживается намеренно.
Таким образом, сброс после ожидания является ожидаемым исходом теста.
Второй опыт дошёл до успешного сравнения всех 122880 пикселей. Установленных
признаков падения до завершения рисования в этих двух опытах нет.
Build ID из RAM не извлечён; привязка опирается на PC/LR/SP и сохранённый журнал
прошивки. Это ограничение остаётся явно зафиксированным.

ESR_EL2=0x5e000000 даёт EC=0x17, класс SMC64, а не Data Abort.
Его нельзя трактовать как свидетельство ошибки чтения framebuffer; регистр не
является историей всех исключений и может относиться к другому событию.
FAR_EL2 в этом контексте также не выдаёт достоверный адрес сбоя framebuffer.
Справочник Arm: https://documentation-service.arm.com/static/67e40f3398aa3c3b6eea6a85

## Результаты проверки кода и артефактов

- Entry сохраняет аргументы до вызова C, выделяет собственный 16-KiB стек,
  выравнивает его на 16 байт. Record и stack не пересекаются.
- MMU/D-cache/endianness/CurrentEL проверяются до записей; неподдержанные
  состояния уходят в отдельный цикл. SIMD не требуется сборкой C.
- В ELF нет неразрешённых символов и незавершённых relocations; payload содержит
  весь стек и данные, BSS запрещён linker assertion.
- Gzip в каждом boot image распаковывается в точный сохранённый raw файл.
  Header page совпадает с исходным boot_b за исключением kernel_size; размеры
  ARM64 Image совпадают с длиной raw.
- Прямоугольник ограничен 640×192, непрозрачный BGRA, stride=4992. Запись не
  затрагивает padding и соседние буферы в проверенных сценариях.
- Readback failure проверен внесением повреждения перед чтением: код идёт
  в ветку ошибки. Success не является безусловным продолжением функции.
- Ramoops пишет только существующий console slice, размещает build ID/CRC,
  проверяет границы/переполнения и совместимый порядок кольца.

Проверки: unittest discovery — 11 тестов, включая варианты EL/баз/отказов;
четыре C-набора framebuffer/marker/readback/ramoops — ASan+UBSan, без ошибок.
Отчёты `evidence/code-audit/artifact-checks.json` и `host-tests.txt`.
Эмуляция не моделирует настоящие bus faults, stage-2 и reset retention.

## Что действительно отсутствует или требует исправления

1. **Нет передачи нового кадра.** Первые probe только меняют RAM. Stock LK
   после этого выполняет cache clean, display-path start, mutex trigger и DSI
   queue/start. Перенос этих действий ещё не реализован. Для command-mode
   панели это основная рабочая гипотеза отсутствия маркера, а не доказанный
   неправильный адрес. Детали: DISPLAY-REGISTER-AUDIT.md.
2. **Не доказан handoff mapping.** Адрес доходит до регистра OVL в проверке
   точного BL2, но CPU stage-2 и display IOMMU после передачи управления не
   восстановлены. Подробности: FRAMEBUFFER-PREFLASH-VERIFICATION.md.
3. **Нет собственных exception vectors.** DAIF маскирует асинхронные события,
   но не устраняет синхронные исключения. В случае нового fault у probe пока
   нет своего обработчика ESR/ELR/FAR. Это пробел наблюдаемости, не установленная
   причина первых двух результатов. Перед расширением MMIO нужен отдельный
   проект и fault-injection проверка обработчика; автоматическое добавление
   непроверенных vectors изменило бы пока ещё непроверенный ramoops-опыт.
4. **Первый marker API игнорирует отказ fb_fill_rect.** Возврат из marker сам
   по себе не доказывает запись. Во втором опыте этот недостаток диагностики
   компенсирован проверкой всех пикселей. С фиксированной валидной поверхностью
   отказ не воспроизведён. Для общего драйвера следует возвращать draw status.
5. **Ramoops пока не проверен на телефоне и не рисует на экран.** Отсутствие
   изменения изображения в следующем опыте не будет признаком его падения.
   Сохранность DRAM через watchdog→fastboot→Android требует отдельной проверки.

## Найденная и исправленная ошибка инструмента

В collect_probe_ramoops.py код возврата ADB принимался за результат remote cat.
На этом устройстве отсутствующий console-ramoops-0 выдаёт текст ошибки в stdout,
но transport returncode=0. Это воспроизведено повторным чтением.

Добавлены уникальный завершающий маркер и код remote-команды. Без завершённой
передачи или при remote error файл сохраняется как .failed-output, manifest
помечает complete=false. Проверены binary roundtrip, remote error и оборванная
передача. Новый capture: evidence/raw/code-audit-capture/manifest.json;
отсутствующая console теперь корректно имеет remote_returncode=1.

Старые дампы не переписаны, образы не пересобраны и их хеши не изменились.
Абсолютное отсутствие всех возможных аппаратных ошибок этим аудитом не
доказывается. Он существенно сужает поиск: предыдущие probe дошли до штатной
остановки, следующий предмет расследования — физическое отображение и передача
пикселей, с более надёжным журналом и диагностикой исключений.
