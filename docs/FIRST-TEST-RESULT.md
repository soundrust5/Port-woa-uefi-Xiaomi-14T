# Первый аппаратный опыт: пробник исполнился, метка не появилась

Образ `348d71dbe8ef1065055024d08731995371433a8180ebf21ccee23bfce56a9922` записан в boot_b; пользователь наблюдал Mi logo, затем watchdog и самостоятельно вернулся в fastboot. После этого исходный boot_b восстановлен. Android успешно завершил загрузку, root доступен; SHA-256 boot_b совпадает с копией восстановления: `fa01819342dd24164dea568f88f9715bc3132f738a68c49453907982946c1113`.

## Что показали журналы

Новый `/proc/pl_lk` снят, но его сохранённый буфер обрывается до распаковки kernel и передачи управления. Сообщения `invalid boot image header`, ошибки AVB для init_boot/vendor_boot и `lcm is cmd mode ... update is null` присутствовали также в исходном рабочем журнале до опыта. Они не устанавливают причину отсутствия метки. Pstore пуст; `/proc/last_kmsg` отсутствует.

Обнаружен свежий отчёт `/data/vendor/aee_exp/db.fatal.03.HWT` от 14 сентября 22:42 и скопирован на ПК. Отдельно снят expdb, 134217728 байт, SHA-256 `9283837a9c7b05adcfa5405ff748426fe688c9323994b63f2da2308309b49c3f`. В его хвосте сохранился watchdog dump с uptime около 33.63 секунды.

| Регистр | Значение | Совпадение с точным ELF пробника |
|---|---|---|
| PC | `0x40000104` | Ветка назад к WFE в `diagnostic_park`, после рисования |
| LR | `0x400000fc` | Адрес возврата из `diagnostic_marker`, следующий DSB |
| SP | `0x400044c0` | `__stack_end`, верх собственного стека |
| PSTATE | `0x600003c5` | EL1h с масками DAIF |
| SCTLR_EL1 | `0x30d00800` | M=0, C=0, EE=0 |
| HCR_EL2 | `0x100030080080001` | VM=1: второй уровень трансляции включён |

Совместное совпадение PC, LR, SP и записанного опыта даёт сильное аппаратное доказательство: пробник был загружен по `0x40000000`, прошёл вход и вернулся из функции рисования. Он остановился в предусмотренном цикле ожидания, где его и застал watchdog. Это не ветка `diagnostic_unsupported` (`0x40000108`).

Проверка воспроизводится командой `python tools/verify_first_watchdog.py`: она проверяет хеш expdb и payload, извлекает символы ELF, декодирует цель BL и сверяет байты WFE/branch/DSB. Отчёт — `evidence/first-test-watchdog-analysis.json`; исходный фрагмент — `evidence/extracted/first-test-expdb/probe-watchdog.txt`. Сам build ID в дампе не найден, поэтому атрибуция основана на точной тройке адресов и истории опыта.

## Следующий предмет проверки

Нельзя больше считать этот результат отказом исполнения kernel payload. Нужно установить, куда ведёт IPA framebuffer при включённом stage-2, и что требуется панели для обновления после LK: scanout, command-mode trigger/TE/CMDQ, сохранённое состояние display pipeline. Возврат из функции рисования ещё не доказывает отображение её записей на панели.

Операции восстановления и все снятые данные находятся в `evidence/raw/first-test-recovery/`. Android оставлен работающим; новых пробных прошивок в ходе диагностики не было.
