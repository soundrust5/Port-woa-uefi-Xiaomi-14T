# Eight CPU Windows ACPI candidate

User observed full Windows desktop but unusably slow first login. Existing
firmware deliberately published only the boot CPU (Cortex-A510, MPIDR0,
MIDR411fd461). Legacy diagnostic restriction had not yet been expanded.

Captured DT contains eight PSCI CPUs at MPIDRs0,100,200,300,400,500,600,700:
four Cortex-A510 and four Cortex-A715. Node names are not MPIDRs: e.g.
/cpus/cpu@100 has reg400. Generator uses reg-derived affinities, not names.

New --all-cpus template generates eight ACPI0007 namespace objects with UID0..7,
and eight matching MADT GICC entries. Boot CPU is first. GICR base placeholders
for secondary CPUs are zero until runtime discovery; no guessed strides.
EfficiencyClass0 forA510,1 forA715; this does not implement DVFS/CPPC.

Runtime in DegasAcpiDxe scans only the DT-mapped GICR region0c440000+200000,
using GICR_TYPER affinity and Last/VLPIS-defined frame stride. Requires a unique
redistributor for each MPIDR and a complete Last-terminated scan. Queries
PSCI_FEATURES(CPU_ON64) and AFFINITY_INFO64 for every CPU; does not callCPU_ON.
Boot CPU must beON and all secondary CPUsOFF. Only after all checks pass are
all eight GICC entries enabled and actual GICR bases filled; table checksum
recalculated before publication. Otherwise only boot CPU stays enabled and
the reason is logged. Windows, not UEFI, performs subsequent AP startup.

Firmware PcdCoreCount intentionally stays1 because SEC itself starts no AP and
uses the existing primary stack layout. It does not limit Windows MADT count.
UFS/touch/GCE/RAM/GPT/Windows installation and CPU voltages/clocks unchanged.
Known single-CPU rollback image remains artifacts/degas-gpt-identity-crc-v1.

Validation: four Python ACPI tests passed, including independent eight GICC
UID/MPIDR/flags/efficiency/base-placeholder and namespace checks. Actual pure
GICR discovery function passed36895 checks each under GCC/Clang ASan+UBSan,
including all256 VLPIS combinations, eight affinity permutations, duplicates,
early/missingLast, overflow and region bounds. iASL and ARM64 UEFI build passed.
Build end19:50:39 Moscow,27October2026. Hardware outcome still pending.

Next validation: Windows Task Manager must show8 logical processors and desktop
responsiveness; runtime log DEGAS SMP enabled=8 is preboot enumeration proof,
not independent proof of Windows successfully starting allAPs.

## Read-only follow-up audit

User observed ACPI CPUS 8/8, GIC 0, PSCI 0, STATE 0. Fresh retained
console captured in evidence/raw/2026-10-27-degas-smp-status-v2-result.
Live ESP BCD copied read-only to artifacts/degas/runtime-log/BCD.live and
decoded with hivex after host bcdedit access was denied. No numproc/onecpu
or processor-group restrictions occur in any object, including inherited
objects. Four ACPI generator tests passed again.

Remaining distinction: PSCI_FEATURES(CPU_ON64)=0 proves availability, not
successful AP execution. AFFINITY_INFO=OFF before boot is expected, not
an AP startup result. Actual Windows CPU_ON, AP interrupt/timer operation
and OS active count remain unobserved. Bad GUI performance alone proves
neither single-CPU operation nor successful SMP. No CPPC/DVFS support is
implemented; eight online CPUs would not independently prove correct
operating frequency or eliminate storage/polling/display bottlenecks.

Runtime logger built in tools/degas_runtime.c. Deployment did NOT succeed:
ntfs-3g fell back to read-only because of unsafe cached NTFS state. No
SYSTEM hive or executable changed on the phone. A normal Windows shutdown
is needed before staging user-startup telemetry. The dirty hive was not
edited and its transaction logs were not removed.
