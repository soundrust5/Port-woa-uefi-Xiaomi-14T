# Первый проход обследования: реальные результаты

Дополнение после первого прохода: [сверка памяти и резервов](MEMORY-RECONCILIATION.md), [контракт framebuffer](FRAMEBUFFER-CONTRACT.md). Эти документы содержат позднейшие данные PL/LK, memblock, CMA и точного установленного драйвера.

2026-09-14. Источники — подключённый Xiaomi 14T через rooted adb и локальный архив прошивки. Телефон не перезагружался и не прошивался. Чтения произвольной физической памяти и MMIO не выполнялись.

## Устройство

- ADB: `degas`, модель `2406APNFAG`; root подтверждён `uid=0`, контекст KernelSU.
- Android сообщает HyperOS `OS3.0.303.0.WNEEUXM`, Android 16.
- Работающее ядро: `6.1.138-android14-11-g44bda9e8f6e9-ab13792638`, AArch64, page size 4096.
- Текущий bootconfig указывает слот `_b`, `dtb_idx=0`, `dtbo_idx=0`, `unlocked/orange`. Отдельные свойства Android могут подменяться модулями.
- Накопитель сообщает `SKhynix HN8T174EJKX075`, ревизия `X205`. User LUN `/dev/block/sdc`: 264509587456 байт, логический блок 4096.

## Память и первые адреса

Все адреса ниже — данные описания платформы, а не разрешение на запись. Полную карту и будущие области FD/heap/stack ещё нужно согласовать.

В [MEMORY-MAP-INITIAL.md](MEMORY-MAP-INITIAL.md) перечислены 52 reg-диапазона reserved-memory и 4 узла с size без статической базы. Резервы ещё не превращены в карту аллокатора.

| Объект | Значение | Основание / ограничение |
|---|---|---|
| DRAM | base `0x40000000`, size `0x300000000` (12 ГиБ), end exclusive `0x340000000` | Live DT `/memory/reg`, размер также указан в bootconfig; внутри есть reserved ranges |
| Framebuffer reserve | base `0xFCC2F000`, size `0x033D0000`, end exclusive `0xFFFFF000` | Совпадает в chosen auxiliary properties и `/reserved-memory/mblock-15-framebuffer/reg`; это один источник boot handoff в двух местах |
| GICD / GICR | iomem: `0x0C400000–0x0C43FFFF` / `0x0C440000–0x0C63FFFF` | Диапазоны выделены работающим ядром; поведение на входе UEFI не измерялось |
| UART-контроллеры | `0x11001000`, `0x11002000`, `0x11003000`, `0x11004000`, по `0x1000` | DT `serial` nodes; физическая доступность и clock/pinmux не подтверждены |
| AP watchdog | base `0x1C00A000`, size `0x100` | DT `mediatek,mt6897-wdt`; offset/key/состояние не установлены |
| UFS host | base `0x112B0000`, size `0x3000` | DT ufshci; bootconfig тоже указывает `112b0000.ufshci` |
| DSI0 | base `0x1400D000`, size `0x1000` | Live DT; не выполнять запись без драйверного контракта |
| PSCI | compatible `arm,psci-1.0`, method `smc` | Объявлено в DT; не результат вызова PSCI_VERSION |

Числовые значения из `reg` для I2C/SPI/CPU и нетривиальных bus mappings не объявлены физическими MMIO-адресами. Инвентаризатор сохраняет неразрешённые записи и предупреждения.

## Что известно об экране

В Android нет `/dev/graphics` и `/sys/class/graphics`; подключён DRM `DSI-1`, разрешение 1220×2712. DP-коннектор перечислен как disconnected: это не доказательство работоспособного внешнего видеовыхода телефона.

В cmdline присутствует имя `panel-n12a-36-02-0b-dsc-cmd`; в DT есть варианты панелей. Декодирование raw `atag,videolfb` по исторической открытой MediaTek-структуре даёт `n12a_36_02_0b_dsc_cmd_lcm_drv` и согласованные base/size. Точный consumer MT6897 ещё не найден, а размеры строки/формат пикселей этот тег не содержит; подробности в MU-PLATFORM-REQUIREMENTS.md. Дальнейшая проверка драйвера и LK должна установить полный контракт панели.

У нескольких текущих DRM framebuffer 1220×2712 зафиксированы `AB24 little-endian`, modifier 0, pitch 4992 байта. Эти данные относятся к Android. Boot framebuffer по адресу из chosen может иметь другой формат/stride. Нельзя связывать их без проверки источника и жизненного цикла буфера.

## Разметка после пользовательских изменений

Пользователь подтвердил создание отдельного раздела за счёт userdata. Текущая GPT содержит 94 раздела, включая:

| Раздел | Начало, байт | Размер, байт | Размер, ГиБ |
|---|---:|---:|---:|
| userdata | 12507414528 | 107374182400 | 100 |
| linux_root | 119881596928 | 144611180544 | ≈134,68 |

CRC primary/backup и записи согласованы, пересечений нет. Проверка GPT не является проверкой целостности F2FS/ext4 или пригодности linux_root для установки ОС. Файловая система linux_root ещё не исследована.

Заводской `PGPT_UFS` не является готовой копией GPT этого телефона: его header CRC и entry CRC равны нулю, last usable LBA также ноль. Возможно, это шаблон для инструментов прошивки; такое назначение ещё не подтверждено. Для восстановления сохраняем реальные метаданные телефона. Особые адреса scatter (`pgpt/sgpt/flashinfo`) требуют интерпретации инструментом, а не прямого переноса в GPT.

## Различия с заводскими образами

- `boot_a`, `boot_b`, `dtbo_a`, `dtbo_b` полностью совпадают с файлами из архива.
- `init_boot_a/b` и `vendor_boot_a/b` отличаются. Конкретную принадлежность изменений KernelSU/TWRP устанавливаем по содержимому, а не по хешу.
- Для `lk_b`, `tee_b`, `gz_b` и `vbmeta*_b` префикс длиной заводского файла совпадает; сами разделы больше. Это не утверждение о полном совпадении разделов.
- Соответствующие компоненты слота A отличаются. Не считаем слот A запасным рабочим вариантом без отдельной проверки.

Полная матрица — `evidence/extracted/2026-09-14/stock-live-comparison.json`.

## Проверки и ограничения инструментов

AOSP unpack_bootimg закреплён на commit `d2bb0af5ba6d3198a3e99529c97eda1be0b5a093`, SHA-256 записан в provenance. На Windows ссылки с именами ramdisk материализованы копиями тех же файлов; исходник AOSP не изменён. Пределы kernel/ramdisk/DTB и извлечённые байты проверены отдельно.

DTC 1.7.2 успешно декомпилировал деревья. Vendor DT выдаёт предупреждения, в том числе отсутствующие cell declarations у некоторых I2C-узлов; логи сохранены, деревья не исправлялись. Ранние неудачные локальные попытки распаковки сохранены в других каталогах; полный результат находится только в `boot-images-complete`.

Root не дал доступ к двум debugfs summary путям clocks/regulators. SELinux и настройки устройства ради этого не менялись. Часть ошибок чтения adb exec-out выводит в stdout; наличие файла и код 0 сами по себе не означают, что запрошенные данные получены.

## Что ещё не завершено

В `evidence/raw/2026-09-14-followup/dmesg-ramoops.txt` обнаружена историческая метка `DEGAS_DISPLAY_GRANULAR_331`, `BUILD=0.03r8r26` и бинарные данные. Формат, происхождение и достигнутая стадия пока не установлены. Это след предыдущей попытки, а не результат текущего проекта и не самостоятельное доказательство запуска UEFI; сохранить и сопоставить со старым кодом, если он доступен.

Нет полного анализа carveouts, vendor ATAG/mblock, всех драйверных привязок, LK handoff, CPU state при входе, безопасных областей FD/stack/heap и boot framebuffer stride/format. Поздний dmesg может не содержать ранние сообщения; pstore относится к предыдущему запуску и требует отдельной датировки. Обследование продолжается по `HARDWARE-SURVEY-PLAN.md`; аппаратная сборка ещё не готовится.
