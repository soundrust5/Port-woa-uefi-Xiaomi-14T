# Экран после первого опыта

Первый опыт доказал выполнение кода до остановки после `diagnostic_marker`; изображения не было. Рабочий адрес образа и стек уже подтверждены watchdog-дампом. Здесь разбираются две оставшиеся неопределённости, без смены адреса framebuffer наугад.

## Уровни трансляции

В дампе SCTLR_EL1.M=0 и SCTLR_EL1.C=0. Одновременно HCR_EL2.VM=1. Поэтому адрес `0xfcc2f000`, использованный кодом EL1, ещё проходит stage-2; выключение MMU EL1 не обходит гипервизор.

Дамп содержит **TTBR0_EL2**, а не **VTTBR_EL2**. Подставлять его как корень stage-2 таблиц нельзя. VTTBR_EL2 и VTCR_EL2 не сохранены в доступном фрагменте, поэтому mapping framebuffer до physical address по нему не восстановлен. Сам VM=1 не доказывает неправильное отображение — он лишь оставляет этот вопрос открытым. Адрес видеобуфера из LK/DT остаётся доказанным для той стадии.

## Обновление в точном LK

Вызовы воспроизводимо извлечены `tools/extract_display_update.py` в `evidence/extracted/2026-09-14/lk-analysis/display-update-chain.asm`:

- `0xffff00005074ee18..0xffff00005074ee2c` передаёт область framebuffer в функцию cache clean и затем переходит в отдельную функцию обновления `0xffff0000507504d8`.
- Cache clean `0xffff0000507056a4` использует `dc cvac` по 64-байтовым линиям и заканчивается `dsb sy`.
- Функция обновления вызывает `0xffff00005074e920` (её диагностические строки называют `disp_lcm_update`), затем продолжает в `0xffff000050748ed0`, где перебираются модули display path и вызываются callbacks.

Таким образом, штатный путь содержит действия помимо записи в RAM. Сообщение об отсутствующем panel-update callback не обрывает весь этот путь: следующий вызов display path остаётся в коде. Полный набор MMIO для самостоятельного запуска refresh пока не перенесён и не проверен. Нельзя вызывать эти LK-функции по их прежним VA из нового payload: контекст, страницы, глобальные указатели и время жизни LK не принадлежат нашему коду.

## Второй измерительный шаг

Readback-вариант рисует ту же ограниченную метку, затем сравнивает все её пиксели чтением через тот же guest-visible адрес. Результат кодируется разными WFE-циклами: `diagnostic_readback_ok` либо `diagnostic_readback_failed`. Отдельно сохраняется `diagnostic_unsupported` для неподдержанного состояния CPU. Точные offsets публикуются в манифесте каждой сборки.

Если watchdog застанет `readback_ok`, CPU видит ожидаемые байты после записи; тогда проверяем scanout/refresh и соответствие гостевого адреса реальной поверхности. Это ещё не доказательство правильной stage-2 карты или обновления панели. `readback_failed` укажет на несовпадение прочитанных пикселей. Зависание до обоих циклов потребует отдельной локализации чтения/исключения. Вариант не программирует DSI, clocks, watchdog или гипервизор.

Первый образ и его ELF сохранены отдельно. Android остаётся работающим; подготовка второго варианта не запускает его автоматически.
