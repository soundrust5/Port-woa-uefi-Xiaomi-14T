# Второй тест: чтение framebuffer

После watchdog пользователь вернул телефон в fastboot. Восстановлен исходный
boot_b; SHA-256 на телефоне совпал с резервной копией. Android завершил загрузку
(sys.boot_completed=1), root доступен.

Образ boot-readback.img: SHA-256
`6a5f8618fef58a8a11e733213ae1ec0f8e38284e6f4136e74df22ae72a6598fc`.
Полный дамп expdb: `evidence/raw/second-test-recovery/expdb-full.img`, 134217728 байт.
Первый захват expdb.img оказался неполным (91790848 байт), несмотря на код возврата 0;
он сохранён как свидетельство ошибки захвата и для анализа результата не используется.
Свежий архив AEE db.fatal.01.HWT сохранён в aee-HWT.tar.

Скрипт `tools/verify_second_watchdog.py` проверяет хеши, символы ELF, инструкцию
вызова и цикл остановки. Результат: `evidence/second-test-watchdog-analysis.json`.

В expdb по смещению 0x7efaa19:
- PC = 0x4000011c — переход в цикле diagnostic_readback_ok;
- LR = 0x400000fc — возврат из diagnostic_marker_readback;
- SP = 0x40004680 — конец стека именно второго образа;
- согласованная база загрузки = 0x40000000.

Это сильное свидетельство, что запись маркера и сравнение всех 640×192 пикселей
завершились успешно. Проверены байты через адрес, видимый CPU; соответствие этого
адреса физическому scanout и обновление панели остаются непроверенными.
Старый дамп первого опыта также остался в expdb, причём по большему смещению:
положение записи в файле не определяет её новизну.

# Журнал в RAM: следующий этап наблюдаемости

В entry.S уже есть 160-байтная запись DEGASD01 с регистрами и build ID. Она лежит
внутри загруженного образа; сохранение при следующей загрузке не обеспечено.
В текущем захвате /sys/fs/pstore пуст. Исторические ramoops из первичного сбора
содержали старый DEGAS_DISPLAY_GRANULAR_331 (см. HARDWARE-SURVEY-INITIAL.md),
но это не доказывает пригодность того же механизма в нынешней загрузочной цепочке.

План реализации:
1. Проверить текущие DT/kernel ramoops, ram_console и форматы AEE/log_store;
   установить владельцев, очистку и сохранение памяти при watchdog и проходе через fastboot.
2. Выбрать область только после проверки владения и исключения из аллокаторов
   загрузчиков, Mu и Android. Не использовать чужой reserved-memory как свободный буфер.
3. Сначала записать небольшой уникальный маркер с build ID, длиной и CRC и доказать
   его извлечение после reset. Наличие root само по себе не обеспечивает доступ к RAM.
4. После проверки сохранения реализовать кольцевой журнал: номер записи, стадия,
   сообщение, CRC, публикация завершённой записи последней операцией; учесть cache/barriers.
5. Подключить ранний ассемблерный writer и Mu DebugLib к одному формату, подготовить
   Android reader или извлечение из подтверждённого crash dump.

Ramoops требует памяти, переживающей reset, и согласованного резервирования:
https://cdn.kernel.org/doc/html/latest/admin-guide/ramoops.html
Произвольная текстовая запись в его область не станет автоматически pstore-журналом.
Пока надёжно подтверждён канал PC/LR/SP через watchdog → expdb; его сохраняем
как независимый индикатор прогресса при разработке полноценного журнала.
