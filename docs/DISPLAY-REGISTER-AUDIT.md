# Аудит display update после второго теста

Снимок 2026-09-14. Это read-only разбор exact main LK и сохранённого
журнала LK/BL2. Адреса вида `0xffff0000...` ниже являются виртуальными
адресами внутри старого LK. Они не являются адресами, по которым новый EL1
payload может безопасно вызывать функции или обращаться к MMIO.

## Результат

Ошибка адреса, pitch, формата или геометрического положения метки имеющимися
данными не подтверждается. Метка записывается с начала основной поверхности:

| Параметр | Значение |
|---|---:|
| Base | `0xfcc2f000` |
| Pitch | `4992 = 0x1380` байт |
| Видимая область | `1220 x 2712`, BGRA8888 |
| Метка | `640 x 192`, начало `(0,0)` |
| Последняя строка метки | offset `191 * 4992 = 0xe8c80` |
| Конец метки в последней строке | offset `0xe9680`, exclusive |
| Конец видимых строк | offset `0xce9400`, exclusive |
| Конец выровненного кадра | offset `0xcf3000`, exclusive |

Последний байт метки имеет offset `0xe967f`; вся метка попадает в первые 192
видимые строки и первые 640 из 1220 видимых пикселей. LK logo writer имеет
rotation 0. Значения `0xffff00ff` и `0xff00ffff` дают соответственно байты
`ff 00 ff ff` и `ff ff 00 ff`, что согласуется с доказанным BGRA layout и
непрозрачным alpha.

Watchdog второго теста (`PC=0x4000011c`, `LR=0x400000fc`,
`SP=0x40004680`) доказывает завершение сравнения всех `640 x 192` пикселей
через CPU-visible адрес. Это исключает обычную ошибку stores/readback в этом
диапазоне, но не доказывает, что stage-2 направляет IPA `0xfcc2f000` именно в
память активного scanout.

## Точная цепочка main LK

Воспроизводимый extractor:
[`tools/extract_display_update.py`](../tools/extract_display_update.py).
Полный выбранный листинг:
[`display-update-chain.asm`](../evidence/extracted/2026-09-14/lk-analysis/display-update-chain.asm).
Extractor проверяет SHA-256 exact main-LK payload
`6afd84aefda089681f0ec4a224c6710228f525ec312bfa2532977be9e4496580`.

Цепочка после штатной записи framebuffer:

1. `0xffff00005074ee18` передаёт base framebuffer в cache-clean
   `0xffff0000507056a4`; длина получена предыдущим вызовом
   `0xffff000050750e78`.
2. `0xffff0000507056a4` выполняет `dc cvac` по 64-байтовым линиям и
   заканчивает `dsb sy`.
3. `0xffff00005074ee2c` переходит в display-update routine
   `0xffff0000507504d8`.
4. `0xffff0000507506f0` вызывает wrapper `0xffff00005074e920`, который
   читает panel callback по `[driver + 0x50]`.
5. `0xffff000050750734` вызывает проход по start callbacks
   `0xffff000050748ed0`; тот читает callback по `[module_driver + 0x20]`.
6. `0xffff000050750780` вызывает `0xffff0000507495b4`; тот читает callback
   по `[module_driver + 0x28]`.
7. `0xffff0000507507bc` вызывает последующую path routine
   `0xffff000050749864`.

Main display path создаётся как scenario 3: `mov w0,#3` по
`0xffff00005074e224`, затем `bl 0xffff0000507483d4` по
`0xffff00005074e22c`. Scenario table находится в exact payload по file offset
`0xe2998 + 3 * 0xc8` и содержит `[46, 43, -1]`.

Runtime driver table строит функция `0xffff0000507482d8`: она копирует по два
указателя из 96 записей source table в BSS table
`0xffff00005082f578`. Реконструкция ровно этого цикла даёт:

| Module | Driver object | `+0x20` | `+0x28` |
|---:|---:|---:|---:|
| 46 | `NULL` | — | — |
| 43 | `0xffff0000507df9f8` | `0xffff000050746c8c` | `0xffff000050746e5c` |

Первое поле driver object равно `0x2b` (43). Указатель выбранного panel driver
`n12a_36_02_0b_dsc_cmd_lcm_drv` равен `0xffff0000507f8828`; его поле `+0x50`
равно `NULL`. Поэтому wrapper panel update не вызывает panel-specific update
callback. Его отсутствие не прекращает внешний update routine: start и
следующий callback модуля 43 находятся после него и вызываются независимо.

## Записи callback модуля 43

Строка, переданная диагностическому print из функции
`0xffff000050746c8c`, равна `ddp_dsi_start`. Функция содержит два режима,
зависящие от runtime поля `0xffff00005082e570`; перечисленные ниже операции
нельзя сводить к одному безусловному списку.

Для входного module 43 и ветви, в которой он заменён на module 45,
`0xffff000050746c8c` выполняет read/modify/write относительно exact LK VA
base `0xffff00001400d000` и `0xffff00001420d000`. В листинге видны записи:

- `base1 + 0x190`: последовательно OR `0x2`, затем OR `0x4`;
- `base0 + 0x000`: clear bit 0;
- `base1 + 0x000`: clear bit 0;
- условно `base1 + 0x010`: set bit 4;
- `base0 + 0x008` и `base1 + 0x008`: zero;
- `base0 + 0x014` и `base1 + 0x014`: вставка runtime mode bits;
- `base0 + 0x100` и `base1 + 0x100`: `0x55` либо `0xaa` по runtime state;
- `base0 + 0x104` и `base1 + 0x104`: set bit 0.

Callback `0xffff000050746e5c` сначала формирует immediate `0x002c3909` и при
нулевом runtime flag передаёт его в `0xffff0000507455d8`. Затем он toggles
bit 0 у `base0 + 0x000`; в dual branch также меняет bit 0 у
`base1 + 0x000` и bit 4 у `base1 + 0x010`. В конце callback выполняет только
reads `baseN + 0x160/0x164`, `baseN + 0x168` и `baseN + 0x16c`.

Это exact LK VA и offsets. Их physical mapping и допустимость доступа из
текущего EL1/stage-2 режима здесь не утверждаются.

**Исправление после проверки главным агентом:** двухконтроллерный список выше
относится именно к runtime remap 43 → 45 при поле 0x5082e570 == 2.
Без remap ветка 43 использует только base0: +0x190 OR2/OR4, +8=0,
+0x14 получает mode, +0x100=0x55/0xaa, +0x104 OR1. Нельзя смешивать эти ветви.

## Дополнительная проверка главным агентом

Разбор 0xffff0000507495b4 подтвердил: перед циклом вызовов driver +0x28
исполняется helper 0xffff00005074cbf0. Он записывает ноль в block+8 и единицу
в block+0x20+(mutex_id<<5). Для scenario 3 используются LK VA blocks
0xffff000014001000 и 0xffff000014401000; дополнительные 0x14201000/0x14601000
включаются только для scenario 0x12. Адреса получены двойным чтением таблиц
из точного бинарника, а не подстановкой по названию SoC. Linux iomem связывает
соответствующие физические блоки с disp-mutex0; mapping в payload ещё не проверен.

Таким образом, перенос одного DSI_START недостаточен для воспроизведения
штатного trigger path: LK предварительно запускает display mutex. DSI queue
writer проверяет mode/busy, пишет очередь по отдельной таблице base (0x1400dd00
и 0x1420dd00 в LK VA) и количество в DSI+0x60. Это не одна безусловная запись.

Рабочая гипотеза главного агента: framebuffer адрес/stride не опровергнуты;
в probe отсутствует необходимый этап передачи кадра command-mode панели.
Чтобы перейти от этой гипотезы к исправлению, нужны наблюдения у входа payload:
содержимое исходной logo surface, режим/состояние DSI и mutex, затем сравнение
с точной LK ветвью. Одно совпадение чёрных углов не доказывает соответствие PA:
нужны содержательные участки логотипа или подтверждённая трансляция.
Сначала проверяется сохранение ramoops, чтобы эти наблюдения можно было извлечь.

## Согласование с сохранённым логом

В живом журнале начальная BL2 display path и handoff-adjacent main-LK path
оставили одну наблюдаемую последовательность имён. После main-LK logo writer
строки 7524–7529 содержат:

```text
ddp_dsi_is_busy
ddp_dsi_start
ddp_dsi_start
DSI_set_cmdq
DSI_CMDQ+0000 : 0x002c3909
```

Значение `0x002c3909` совпадает с immediate exact callback
`0xffff000050746e5c`. Более ранняя BL2 последовательность после собственного
logo writer (строки 4006–4011) содержит те же `ddp_dsi_start` и
`DSI_set_cmdq ... 0x002c3909`. Это динамически подтверждает тип пути и команду;
адреса callback выше относятся к exact main LK, а не автоматически к BL2.

## Stage-2: установленная граница доказательства

В watchdog dump `SCTLR_EL1.M=0`, `SCTLR_EL1.C=0`, но
`HCR_EL2.VM=1`. Поэтому EL1 адрес `0xfcc2f000` проходит stage-2 translation.
Дамп сохранил `TTBR0_EL2`, но не `VTTBR_EL2` и не `VTCR_EL2`; восстановить
IPA-to-PA mapping по нему нельзя. Успешный readback доказывает согласованные
CPU reads/writes по одному IPA, но сам по себе не связывает его с DSI scanout.

Этот аудит не переносит старые LK VA в payload и не выводит неизвестные MMIO
адреса из их младших битов.
