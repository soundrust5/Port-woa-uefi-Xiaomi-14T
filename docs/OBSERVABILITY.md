# Доказательство запуска и диагностика

Это проектные критерии. Перечисленные каналы ещё не проверены на нашем телефоне.

## Уровни доказательства

| Наблюдение | Допустимый вывод |
|---|---|
| fastboot принял/записал файл | Операция доставки завершилась; выполнение payload не доказано |
| Висит логотип Xiaomi | Дисплей показывает изображение; последняя выполненная стадия неизвестна |
| Телефон перезапускается | Произошёл reset; причину без дополнительных данных не определяем |
| Появился уникальный маркер текущего payload | Управление дошло как минимум до точки формирования маркера |
| После маркера изменяется счётчик/последовательность | Код продолжал выполняться между наблюдаемыми обновлениями |
| Есть маркеры входа EDK2 и DXE | Выполнение дошло до отмеченных мест в firmware |
| Отдельное EFI-приложение выдаёт результаты Boot Services | EDK2 выполнил приложение и проверенный поднабор служб |

Метка должна включать идентификатор сборки и стадию. Сравниваем два образа с различными заранее заданными метками, чтобы исключить старую картинку или журнал от прошлого запуска. Фиксируем происхождение каждого наблюдения: телефон, UART, USB или эмулятор.

## Возможные каналы

**Унаследованный framebuffer.** Привлекателен, если загрузчик оставляет работающий вывод. До записи выяснить адрес, размер, stride, формат пикселя, резервирование памяти и сохранность display pipeline. Проверить необходимость очистки cache. Физический framebuffer нельзя угадывать по разрешению экрана или адресу из другого порта. Неподвижный логотип не доказывает, что простая запись в RAM обновит панель.

**UART.** Подходит для ранних маркеров и исключений, если доступны контроллер, clock/pinmux и физическое подключение. Адрес, скорость и доступ должны подтверждаться. Отсутствие текста может означать ошибку самого канала. Разборка/пайка пока не включены в выбранный маршрут.

**RAM-журнал.** Полезен только с обоснованной областью, корректными cache/barrier-операциями и реальным способом считывания. Сохранность RAM после reset не гарантирована. Для защиты от старого журнала нужны build ID/счётчик и проверка целостности. Наличие pstore/ramoops у Linux не означает, что произвольный payload автоматически может пользоваться им.

**USB.** Сильное доказательство, если свой код отвечает на запрос и передаёт build ID. Но PHY, clocks, controller и протокол могут потребовать существенной работы. Исчезновение/появление USB-устройства без ответа нашего кода — только косвенный признак. Оставшийся ADB от Android не является отладчиком произвольного UEFI.

**Контролируемая перезагрузка.** Может дать вспомогательное наблюдение после изучения reset/watchdog. Различная задержка сама по себе не доказывает выполнение: похожее поведение бывает у штатного загрузчика и watchdog. Не использовать как единственный критерий M3.

## Проектируемые метки

План меток: P0 вход в payload → P1 сохранение контекста/стек → P2 готовность исключений → P3 минимальное окружение → E0 вход EDK2 → E1 DXE → A0 вход EFI-приложения → A1 проверенные службы.

Порядок подстраивается под доступность канала. Если первый наблюдаемый маркер появляется только после сложного драйвера, участок до него остаётся недиагностируемым. Желательно иметь второй независимый канал, но его отсутствие не должно автоматически превращать USB-драйвер в условие первого опыта.

При исключении сохранять, когда это технически возможно: стадию, build ID, CurrentEL, ESR, ELR, FAR, SP и нужные регистры. Для каждого регистра учитывать текущий Exception Level и доступность чтения. Обработчик с записью в неизвестную память сам может скрыть первичный сбой.

## Разбор неудачного опыта

1. Сверить хеш реально использованного образа, выбранный режим и точную команду.
2. Разделить ошибку транспорта, отказ загрузчика, наблюдение payload и наблюдение EDK2.
3. Найти последнюю подтверждённую метку, а не последнюю строку предполагаемой последовательности.
4. Проверить пригодность канала; отсутствие метки оставить неопределённым, если канал не подтверждён.
5. Изменить одну причину: упаковку, условие входа, карту памяти либо конкретную инициализацию.
6. Повторить с новой меткой и записать результат по шаблону эксперимента.

QEMU-прохождение записывается отдельно от запуска на телефоне. Оно проверяет общий код и механизм теста, не реальный аппаратный контракт MT6897.
