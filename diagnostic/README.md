# Первый код диагностики degas

Это первый самостоятельный ARM64-пробник и библиотека рисования для будущего порта Mu. Полный UEFI для degas ещё не собран. Телефон этим кодом не запускался.

## Что реализовано

- `entry.S`: позиционно-независимый вход, запись исходных x0–x3, SP, DAIF, CurrentEL и SCTLR/TCR/TTBR0/MAIR соответствующего EL. Поддерживаемый путь: EL1 или EL2, little endian, MMU и D-cache выключены. Для неподдерживаемого EL3 или состояния SCTLR код останавливается до записи в память. EL0 не является допустимым входом: привилегированные инструкции могут вызвать исключение.
- Запись `DegasEntryRecord` и стек находятся внутри собственного образа. Стек 16 KiB включён в фактический бинарный файл и Image size; внешнего фиксированного адреса стека нет. Пробник публикует magic `DEGASD01` последним, после остальных полей. Build ID — SHA-256 списка хешей исходников пробника.
- `framebuffer.c`: запись прямоугольника в переданную вызывающим кодом BGRA-поверхность. Все границы и арифметика проверяются до первой записи. Адресное отображение, cache maintenance и обновление DSI остаются обязанностью вызывающего кода.
- `include/degas_display.h`: подтверждённые параметры штатного основного слоя: physical base `0xfcc2f000`, 1220×2712, pitch 4992, ограничение поверхности одним выровненным кадром `0xcf3000`.

Пробник пока не вызывает framebuffer-библиотеку: он сохраняет запись и ждёт. Он не изменяет MMIO, не обслуживает watchdog, не вызывает LK, не устанавливает свои векторы исключений и не переключает MMU/cache. Возможность чтения архитектурных регистров и доступ к собственному образу предполагаются контрактом входа и ещё не измерены на телефоне.

## Сборка и проверки

Из корня проекта в PowerShell:

```powershell
wsl -- bash -c 'cd /mnt/d/Edk2-For-Xiaomi14T && python3 diagnostic/build.py'
python diagnostic/tests/test_entry.py
python diagnostic/tests/test_mu_stack.py
python diagnostic/tests/test_mu_geometry.py
wsl -- bash -c 'cd /mnt/d/Edk2-For-Xiaomi14T && clang -std=c11 -Wall -Wextra -Werror -fsanitize=address,undefined -I diagnostic/include diagnostic/framebuffer.c diagnostic/tests/test_framebuffer.c -o diagnostic/build/test_framebuffer && diagnostic/build/test_framebuffer'
```

Сборка использует Clang/LLD и llvm-objcopy в WSL. Python-тесты используют локальные `tools/vendor/python`: Unicorn 2.1.4 и pyelftools 0.33. Среда Mu подготовлена, SEC и SimpleFbDxe собраны; см. [состояние сборки](../docs/BUILD-STATUS.md). QEMU не подготовлен.

Результаты: `build/entry.elf`, `build/entry.bin`, `build/manifest.json`, отчёты тестов. Бинарник содержит 64-байтовый ARM64 Image header для проверки формата на ПК. Наличие такого header не означает, что Xiaomi LK примет этот образ. Android boot container не создаётся.

Тесты entry выполняют машинные инструкции и проверяют относительное размещение, сохранение аргументов, ограничения записей и ветви отказа. Значения чтений системных регистров подставляются тестом, поскольку Unicorn не воспроизводит весь режим привилегий. Это не проверка реальных EL/cache/DSI на MT6897. Тест Mu stack исполняет фактическое тело `MainEntryPoint` с тестовыми PCD и заглушкой `SecEntry`, не весь Mu.

## Что отделяет этот код от первого аппаратного опыта

Текущий экранный вариант собирается отдельно через `build_marker.py` в `build-marker/`, сохраняя RAM-only вариант в `build/`. Он проверен целиком в Unicorn и упакован в первый экспериментальный boot.img: [артефакты и ограничения](../artifacts/first-test/README.md). Проверка состояний входа остаётся включённой; обновление реальной панели не доказано эмуляцией.

Дополнение после сборки Mu: исследованный путь точного LK требует сжатый kernel payload. `python diagnostic/prepare_kernel.py` создаёт `build/entry.bin.gz`, а `python diagnostic/tests/test_lk_compression.py` проверяет его ветку распознавания на точных инструкциях LK. Это пока только кандидат на ПК, не boot.img. См. [статический контракт LK](../docs/LK-HANDOFF-STATIC.md).

1. Доказать, как LK размещает именно наш payload, какой диапазон остаётся его собственностью и в каком состоянии передаёт управление. Тестовые адреса эмулятора не являются выбором адреса загрузки.
2. Реализовать и проверить способ наблюдения свежей записи либо изображения. Внутренняя запись в RAM пока не имеет подтверждённого канала считывания с телефона; её сохранность после reset не предполагается.
3. Для экранной метки подтвердить сохранность основного слоя, режим обновления панели и cache policy. Затем соединить диагностический вход с ограниченным рисованием. Изменение памяти само по себе не доказывает обновление панели.
4. Определить точный контейнер и путь восстановления одного опыта, после чего собирать аппаратный тестовый образ.

Области FD/heap будущего Mu не назначены. [Карта памяти](../docs/MEMORY-RECONCILIATION.md) и [контракт framebuffer](../docs/FRAMEBUFFER-CONTRACT.md) остаются источниками ограничений.
